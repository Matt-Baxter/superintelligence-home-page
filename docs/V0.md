# Working with v0 (John's bake-off version)

John builds his version of the homepage experience in **v0**; Matt builds his in **Claude**. Both build against the same [shared spec](../specs/001-superintelligence-homepage/spec.md) and [constitution](../.specify/memory/constitution.md); how we compare is in the [contract](../CONTRACT.md). This page covers the v0 side.

## Set up once

1. **Make the branch.** On GitHub, open the branch menu on the repo, type `bakeoff/v0-john`, and create it from `main`.
2. **Import into v0.** In v0, start a new chat from GitHub (**Import → GitHub repository**), pick `Matt-Baxter/superintelligence-home-page`, and choose the `bakeoff/v0-john` branch. If v0 says it can't access the repo, Matt needs to grant the Vercel GitHub app access to it ([DEPLOY.md](DEPLOY.md), step 1).
3. **Keep v0's commits on that branch.** v0 commits to the branch you imported. Never point it at `main`.

## First message to v0 (paste and edit)

> This repo is a Node/Express app with static pages in `public/` and a JSON API in `server.js`. Build against the shared spec in `specs/001-superintelligence-homepage/spec.md` (REQ IDs and Given/When/Then scenarios); this repo's API and data model are in `docs/INTERFACES.md`. Don't change routes, request or response shapes, or the database schema. Build my version of the homepage experience (feed, story page and weekly brief) as pages in `public/` that call the existing `/api/*` routes. Keep plain HTML, CSS and JavaScript (no framework, no build step besides the existing `npm run build`). Keep the existing pages working. Never add Twitter/X sources. Test data must be clearly labelled "Sample".

If you'd rather v0 use Next.js, put that app in its own folder (`apps/v0-home/`), have it call the deployed API, and deploy it as a separate Vercel project. That takes more setup and makes the comparison less direct, so plain pages are the simpler choice.

## Each session

1. Prompt v0, look at its preview, and keep iterating.
2. When a piece works, let v0 commit to `bakeoff/v0-john`.
3. GitHub runs **Preflight** on every push (Actions tab, or the checkmark next to the commit). v0 can't run the local checks, so look for the green check. If it's red, open the run, copy the ✗ line back to v0, and ask it to fix that.
4. Vercel makes a preview link for the branch. Click through it signed in as two different test accounts.
5. **Agent log:** when v0 gets something wrong, write it up yourself in the app's Agent log page, the same day, in your own words. The editor records how the entry was written.

## Finishing the bake-off

1. Open a **draft** pull request from `bakeoff/v0-john` into `main`, titled `Bake-off: v0 version (John)`. Matt does the same from `bakeoff/claude-matt`.
2. Run CLEF or JEV on both against the criteria you agreed on beforehand. Paste its scores and recommendation into both PRs.
3. Both of you sign off, add a change-log row to [CONTRACT.md](../CONTRACT.md) recording the decision and why, then merge the winner (or the agreed merge) and close the other.

## v0 habits to watch for

- **Rewriting the stack:** it may try to convert the project to Next.js or add a database client. Say no and point it back at the contract.
- **Inventing API fields:** it may make up fields the API doesn't return. Compare its calls with the API table in [INTERFACES.md](INTERFACES.md).
- **Dropping existing pages** while it builds new ones. Check that `/sources` and `/lists` still work in the preview.
- **Placeholder data:** it may hard-code fake data instead of calling the API. Real data comes only from `/api/stories` and `/api/brief`.
